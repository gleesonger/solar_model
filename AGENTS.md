# Working on solar_model

- Start with the [documentation index](documentation/index.md), then read the guides for the subsystem you are changing.
- For every code change, review the relevant overview and [implementation documentation](documentation/implementation/index.md) and consider its documented behavior, data contracts, assumptions, and constraints when making the change.
- **Keep documentation up to date with future changes.** Update the relevant Markdown guides in the same change as code, configuration, schema, commands, or styling. Update this file when agent instructions change.
- If a proposed change creates or reveals a major conflict with the documentation, notify the user, explain the conflict, and ask for direction before proceeding with the conflicting change.
- Document verified behavior; keep defects and unresolved design questions in [review findings](documentation/reviews/findings.md). Remove or revise findings when resolved.
- Preserve unrelated working-tree changes. Inspect current source and working-tree differences; Git HEAD alone may not describe local experimental files. Follow the documentation index's source roles: current contracts in subsystem/reference guides, unresolved issues in findings, and dated investigations as historical context. Remove obsolete review diaries and test counts rather than presenting them as current verification.
- Application code lives under `solar_model/`: planning calculations have no storage/network/UI dependency; services assemble inputs and persist results; storage queries have no NiceGUI dependency. Read [code-map.md](documentation/overview/code-map.md) for ownership. Tools run with `python -m solar_model.tools.<name>`.
- Keep the energy-plan optimiser and report-allocation calculations close to basic Python: prefer lists, loops, scalar arithmetic and min/max; use NumPy only where needed. Pass one-dimensional lists directly to CVXPY rather than nested-list constants, whose orientation is ambiguous.
- Use type annotations throughout application code where practical, including function parameters and returns, callbacks, and non-obvious data structures. Prefer concrete types and parameterised collections; reserve `Any` for dynamic library boundaries. Use typing-only imports where needed to preserve dependency boundaries and lazy loading.
- Every configuration value must be explicitly supplied in YAML and the Plan settings editor. Do not add implicit configuration defaults or infer missing values. Nullable settings require explicit `null`, and intentionally empty lists require explicit `[]`. Keep the shipped YAML complete and make missing values fail validation with their full configuration path.
- Prefer single-line expressions and calls where practical. When splitting a call, function signature or collection, place the first argument or entry on a new line, each argument or entry on its own indented line, and the closing bracket on its own line. Preserve meaningful blank-line grouping and short comments.
- Production entry points: `solar_model/runtime/supervisor.py`, `solar_model/runtime/collector.py`, `solar_model/runtime/planner.py`, `solar_model/dashboard/app.py`. Root entry points are compatibility launchers for package modules. Planning/report tools are separate; the application does not send battery-control commands.
- Database measurements use integers scaled by 10,000; SQLAlchemy returns physical units. Raw SQL must convert explicitly. Most measurement timestamps are UTC epoch seconds; device-history timestamps are ISO strings.
- Preserve raw forecast history, snapshot/target-time distinctions, cumulative-counter reset handling, and configured-timezone date boundaries. See [data-model.md](documentation/overview/data-model.md).
- `open_database()` can migrate and backfill a database. Use temporary databases or copies for development; do not use the user's `solar.db` for destructive verification.
- Run commands from the repository root unless a guide specifies otherwise. Configuration and relative database paths resolve from the working directory.
- Keep verification lightweight: run only key targeted tests relevant to the change; do not run the full suite. Run model simulations and performance benchmarks only when the user requests them. For formatting-only changes, use a lightweight syntax/AST or diff check rather than tests. Browser checks need a separate Playwright/browser installation and may otherwise skip.
- Performance experiments must kill any simulation taking longer than five seconds, skip the remaining runs for that test case, and continue with other cases. Report timed-out cases as N/A unless the user explicitly sets a different limit.
- For styling changes, follow [styling.md](documentation/overview/styling.md) and check desktop/mobile layouts, chart legends, and loading/stale states.
