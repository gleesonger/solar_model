# Saved plans and Plan History

Shared background plans are published through `solar.db`. The Markov optimiser remains database-free. Demonstrations and the as-of workbook CLI do not save shared plans.

## Ownership and publication

The supervisor owns three independently restarted services: persisted collector, headless planner and dashboard. `runtime.planner.PlannerService` watches committed readings and hot-reloads energy-plan settings. Its single `runtime.planning_worker.PlanningWorker` calculation process receives at most one job, captures its UTC input cutoff when execution begins, calculates both views, and commits a shared snapshot. The planner records health/publication status in `database_metadata.planning_service_status`.

The dashboard no longer schedules actual plans. `dashboard.plan_store.PlanStore` polls the latest saved ID and service health once per second, reads changed IDs into one shared cache, and notifies connected browsers. It restores the latest saved plan on startup. Planning continues if the dashboard is stopped. Private demonstrations use a separate, on-demand worker with one admitted request server-wide and no queue. They do not save shared plans or compete with the scheduled worker. Each worker retains its own native dispatchers and typed-list support initialisation. The first demonstration can load cached model kernels yet compile per-process support code; later requests reuse that worker. Start logs include operation and worker PID, and model completion logs distinguish model/support compilation and disk/memory reuse.

Both workers use `energy_plan.calculation_timeout_seconds` (explicitly configured; shipped value 300 seconds, including cold process startup). A timeout or process crash terminates/reaps that worker; later jobs create a replacement. Scheduler timeout detection occurs on its one-second loop. Shutdown waits are bounded. A calculation or transaction failure retains the previous published plan; a committed ID can be recovered even if a notification/readback fails. No cleanup runs without submission, and no missed snapshots are fabricated.

## One-table storage contract

Migration `0.3.3` adds `plan_history` and advances `database_metadata.database_version` atomically without rewriting telemetry or forecasts. Normal startup performs the migration; use a temporary database or a copy for development.

Each row identifies `(snapshot_id, view, scenario)`. `view` is `metadata`, `Compact`, `Advanced`, or the optional model `Expected` section. The metadata row uses an empty scenario. `saved_at` is UTC epoch **microseconds**, identifying completion time; `slot` is its integer UTC retention bucket. These differ from measurement timestamps in seconds. Indexes support time/date and slot selection.

`payload` is zlib-compressed UTF-8 JSON, never pickle. It stores a versioned report section as column names, timestamp-column names and chronological row arrays. One section row contains all intervals for a view/scenario, rather than duplicating metadata on every interval. This keeps the single table small while preserving every value needed by the UI. Numeric plan outputs retain their original floating-point precision; they are **not** scaled measurement columns. Missing values become JSON null. Interval timestamps remain full UTC ISO strings. Decoding explicitly accepts ISO8601 with mixed fractional-second precision, including precise worker cutoffs and clock-aligned later boundaries. Totals and display rounding are generated when reading/rendering, not stored as interval rows.

Metadata format version 1 includes execution start/completion, captured source reading, timezone, model, serialized energy-plan settings, the complete next action, capacity/reserve/protection settings, original simulation column/action information and visible-row boundaries. Actual chart observations are not stored in new snapshots. Latest and historical reports both query telemetry separately when loaded; legacy embedded actuals are ignored. Submission no longer rewrites previous metadata to strip observations. The background publication path skips the chart-actuals query entirely. Each new report also retains exact scenario summaries, first-action duration/PV export and initial battery levels, so summaries remain tied to the original calculation. Existing snapshots lacking that metadata use their retained report resolution. Optional Markov expectations remain distinct from stress scenarios.

`planning.plan_report` owns the shared column definitions, period calculations, Compact hourly aggregation, Advanced labels and footer calculations. `services.plan_history.prepare_details()` runs this processing in the worker. The live UI uses these prepared views after loading from storage. Demonstrations reuse the same pure transformations without persistence. `dashboard.components.plan_detail` owns only table rendering and Excel output.

## Retention on successful submission

The entire policy is configured under `energy_plan.history`:

```yaml
history:
  retain_snapshots_frequency_mins: 30
  retain_snapshots_period_days: 30
```

Both values must be explicitly supplied as positive integers. Missing history blocks or values fail configuration validation; the shipped values are 30. Keep the first successful snapshot in each configured UTC interval, with all scenarios and both Compact and Advanced views (including optional model Expected sections), for the configured number of elapsed days. Always protect the latest submitted plan, even if it is outside the retained slot or the application has been idle beyond the period. Superseded intermediate plans are removed at the next successful submission; there is no recent-every-run tier or separate Advanced expiry.

`slot = saved_at // (frequency_mins * 60_000_000)`. A frequency change re-buckets surviving rows atomically before selecting keepers; `database_metadata.plan_history_frequency_mins` records the current bucketing interval. Changing the period/frequency cannot recover snapshots or Advanced data already deleted under an earlier policy. The planner hot-reloads these settings with energy_plan; a save using the new settings applies the new policy. No read or configuration edit itself deletes history.

First-in-slot selection uses completion timestamp then snapshot ID for deterministic ties. Age cutoffs use elapsed UTC time through daylight-saving transitions. If no submission occurs for a week, old data remains until the next successful save catches up. SQLite reuses deleted space; cleanup does not run VACUUM or promise immediate file shrinkage. Retention does not load the archive into application RAM: live plans are shared-cached, and historical reports are loaded on demand.

## UI

There is a single **Plan** tab with the existing action, summaries, scenario controls, chart, Compact/Advanced table and Excel export. Immediately right of **Plan settings** are **Plan date** and **Snapshot** controls. On first load, Plan date is today in the configured timezone and its snapshots load automatically. Snapshot remains blank, so the page follows the latest shared actual plan. The user can change or clear the date. A date filters the available snapshot times but does not itself select a historical plan. Selecting a snapshot pins that report; new shared publications do not replace it. Clearing the snapshot or date resumes latest. Async selection requests are versioned so late reads cannot replace a newer selection. Completed demonstrations also cannot replace a pinned historical selection.

Historical reports use their captured scenario information, first action and exact saved summaries. Saved energy-plan YAML remains archived text: loading a snapshot does not validate it against the current application configuration schema. Plan Settings initially displays that exact stored text for the displayed snapshot, including older settings. Run Demonstration and Save To Disk validate against the current schema and show errors for missing or obsolete settings without changing the saved projection. Load Global explicitly replaces the editor draft with the current live configuration. Retained snapshots offer their original Advanced resolution throughout the retention period. Legacy Compact-only snapshots from an earlier policy still display their saved hourly data and explain why Advanced is unavailable. Actual chart observations are queried from the snapshot-local midnight through the earlier of now and the saved projection horizon, including observations after the original calculation cutoff. Compact charts clip observations to their visible horizon; Advanced can include lookahead. These observations can reflect later historical telemetry corrections; the forecast remains the saved one. While a report is displayed, a per-browser one-minute refresh reloads actuals without changing the forecast, selected snapshot, settings, summaries, legend or zoom. Late reads cannot replace another selected report. Each metric has one legend entry controlling both its solid actuals and dashed forecast lines, including overlapping timestamps. Missing telemetry values remain null, but actual lines join recorded readings across missing samples with a solid stroke, keeping them visually distinct from dashed forecasts. No values are imputed; forecast-only reports still render. Chart legend/zoom and scenario selections survive switches. Neither history selection nor export runs the optimiser.

Date bounds use successive configured-local midnights, preserving 23/25-hour days. Snapshot times include timezone labels for repeated hours. Tables preserve chronological UTC order, existing formatting and totals. Desktop controls remain to the right of settings; on mobile they wrap in the same order within the viewport.

## Verification

Targeted storage/dashboard tests cover precision, retention, rollback, original summaries in historical reports, cache publication and private demonstration admission. `tests/runtime/test_planner.py` runs real spawned calculation processes, injected synthetic collection/planning processes, deadlines, crashes, restarts, Windows descendant cleanup and actual supervisor recovery from a dashboard crash. `tests/browser/test_plan_history.py` exercises a real browser with concurrent synthetic collector/planner processes: today's date and automatically loaded snapshot options, control placement, historical pinning during new publications, chart legend preservation, clearing to latest, historical views, Excel and desktop/mobile widths. `test_plan_tab.py` retains demonstration/settings/rendering checks. These use temporary databases and synthetic measurements/reports. A separate production-worker regression assembles temporary device/history/forecast inputs, executes the real Markov optimiser inside the spawned worker and verifies all nine views after save/readback; live device/provider integration remains separate.

New snapshots identify their model as `markov`. Retired MILP/independent-DP snapshots remain readable as saved data, with their original YAML shown unchanged; running or saving that YAML requires explicit migration to the current flat optimiser schema.

Current settings use numeric `energy_plan.scenario_multiplier` values without scenario probabilities. Archived settings using the old `scenarios` mapping remain unchanged in storage and in Plan Settings; display extracts their original multiplier numbers and ignores their old probabilities. Reusing those archived settings requires explicitly migrating the block before current configuration validation accepts it.

Plan Download Excel uses a single `Plan detail` worksheet. Compact keeps its existing forecast/detail headings and appends comparison columns on each plan interval's row. Advanced uses 52 ordered columns: local/UTC timing and action, tariffs, adjacent forecast/actual power with coverage, battery state/targets, forecast energy, finances, routes/conversions, losses/clipping, and scores. Export variables use explicit `forecast_`/`actual_` names and unit suffixes, with readable spreadsheet headings; battery ending forecast appears once. A six-row metadata block (`snapshot_id`, `model`, `view`, `solar_scenario`, `house_load_scenario`, `report_basis`) precedes the Advanced table, separated by a blank row. Unknown metadata for demonstrations or older reports stays blank. Advanced includes Duration (min) and retains the original subtotal/total contributions. Power comparisons use average kW, with actual minute samples weighted by their overlap with that interval and coverage minutes reported per metric. No missing intervals are filled or extrapolated. Battery comparison uses the forecast ending kWh and latest measured battery reading within the interval through its end, with that reading's UTC timestamp. UTC start/end columns distinguish repeated local hours. Missing/future actuals and all comparison footer cells remain blank. Measurements before the projection or beyond the selected Compact/Advanced horizon are excluded. Export reuses the chart's loaded actuals, independent of zoom/Line/Bar display, without another database read or optimiser run.


On each new shared plan publication, `PlanTab.sync_shared_plan()` refreshes snapshot choices for the currently selected date. A blank Snapshot follows the new report, updating chart and table. A selected snapshot keeps its report and selection while the choices update; if retention removed its database entry, its existing choice remains available while pinned. Refreshes preserve selections made during a pending read and discard results for a superseded date. Service health notifications without a new plan version do not requery snapshot choices. Reconnecting browsers use the same synchronisation path.


Plan publication notifications can reach a connected browser before its initial dashboard has rendered the Plan controls. Snapshot-option refresh defers until both selectors exist, leaving the snapshot version unconsumed. Initial rendering then applies the latest cached plan and loads the current date's choices; subsequent publications use normal live/pinned synchronisation.
