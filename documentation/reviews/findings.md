## Model and data questions requiring decisions

- **Recent Load naming:** the Live/Today **Load** row combines `plant_load_power_kw` (household demand) under Latest with device load-counter energy under Today. The latter appears to include conversion/system losses, while Analysis distinguishes **House Load** from counter **Load**. A single row label cannot describe both consistently; decide whether to split the row or change its energy source. Past actual summaries retain the device-counter basis. House Load (Forecast) now uses integrated household demand in Analysis and the Recent House Load BoD cell; the separate House Load row and Past columns use consistent household-demand actuals. Full-data exports still use the autogenerated label for `plant_load_power_kw`, while chart CSV keeps the internal `load` column.
- **Load energy versus load power (2026-10-26):** read-only inspection of the copied `solar.db` for 00:00–01:00 Europe/Dublin found 60 complete minute samples averaging 0.33675 kW load, while raw lifetime load deltas and the hourly rollup both total 0.70 kWh; the daily load counter also increases by 0.70 kWh between the endpoints. Plant battery discharge/export energy is 5.85/5.15 kWh. Mean battery discharge/inverter AC output is 5.84853/5.49880 kW, leaving approximately 0.35 kW of conversion/system losses; inverter AC output minus grid export agrees with measured household load (0.33697 kW). These observations strongly suggest the device load energy counter includes losses that its load power register excludes; the firmware's exact accounting remains unverified. Register addresses/types/scales match the supplied protocol (30284 power; 30092/30094 energy). Chart aggregation reproduces the stored values. Analysis now exposes integrated House Load alongside the original Load counter. Exact firmware loss accounting remains unverified; existing counter-based energy/cost semantics are retained.
- **Negative adjusted solar:** [operational_model._prediction_fields](../../solar_model/planning/forecasts/solar.py) does not clamp additive residual output. Negative W/Wh is possible by inspection; decide physical bounds and test adverse residuals.
- **Replay parity:** live correction handles future target days in each collection; historical rebuild clears all selected targets but replays only each collection's current local day. Confirm the intended audit coverage before relying on rebuilt future-day vintages.
- **DST representation:** several views use fixed 24 clock-hour buckets, merging repeated hours. Spring DST SQL tests exist; UTC planning arithmetic and both DST transitions now have regression coverage (R13); fixed-clock dashboard views and broader local display still need separate verification.
- **Interval attribution:** counter gaps use the ending timestamp's tariff/hour and PV integration spans the whole gap. Decide acceptable maximum gap and whether tariff/day boundaries require interval splitting.
- **Forecast export meaning:** export aggregation averages cumulative `*_watt_hours` while charts difference them into interval energy. Confirm whether downloads should expose stored provider fields or reproduce chart energy.
- **Scenario interpretation:** optimiser decisions are independent across scenarios. If the goal becomes one executable plan under uncertainty, shared-decision constraints and a control integration would be required.
- **Plan model implementation decisions:** the [proposed plan model](../overview/plan-model.md#63-assumptions-and-unresolved-decisions) specifies a shared next action and normalised cost/protection scoring. Open items include verified EMS command response and handover, consistent usable-energy/SOC conventions, future-date load coverage, input fallback, and approximation/solver tolerances. This is a target design; current planning remains report-only.
- **Validation policy:** unknown YAML keys are ignored and some numeric/site fields lack bounds. Decide whether descriptive keys should be formal fields and other unknown keys rejected.

## Coverage and maintenance gaps

- Chrome Android saved offline pages can preserve dashboard visuals while in-page scripts are inactive. Finite CSS activity indication and an absolute Last reading timestamp reduce ambiguity, but actual saved-page/freeze behaviour still needs verification on Android hardware; desktop Chromium regression checks do not establish it.

- Runtime dependencies remain ranged, with no lockfile. HiGHS is now explicit; package extras declare test, browser and research dependencies.
- Tariff helper logic is duplicated between config validation and economics; changes must preserve matching parity.
- `solar_model/storage/queries/dashboard.py` retains older ORM/pandas calculations used by current adapters or SQL regression comparisons. Remove individual paths only after checking both consumers and independent test references; the unmounted Hourly tab has been removed.
- Independent `check-tariffs` scripts run on import and extraction has a hard-coded external database path; treat them as manual tools.

## First-step action modelling

`simulate_energy_plan` derives first-step operating mode from mutually exclusive forced battery rates. SOC stopping is modelled, including starting beyond the cut-off; self-consumption ignores action SOC cut-offs. The fixed 100 W minimum positive rate distinguishes forcing from zero. PV-first priority and saturation at other equipment/flow limits from the target plan model are not yet fully enforced; scenario flows remain optimisation decisions within the existing equations. Installed-firmware response is also unverified.

- **Simulation result construction:** the current Model to Results section reads `next_action.force_battery_charge_rate`/`force_battery_discharge_rate` before assigning the local `next_action`. After a successful solve this raises `UnboundLocalError`; derive mode from the solved rate variables before constructing `NextAction`. Recorded during the probability-weighting change; not modified as part of that change.
