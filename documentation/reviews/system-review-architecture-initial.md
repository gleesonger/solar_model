## Confirmed findings

### A1 — High: interrupted first hourly backfill is permanently skipped on restart

Category reliability/correctness; high confidence from temporary-DB reproduction. `database.py:666–694`, especially `open_database()` lines 671 and 689–691, detects table existence, creates `sigenstor_hourly`, then performs the historical insertion in a separate transaction. A failure or termination after creation leaves the table present. Every subsequent opener takes the existing-table branch and never backfills it. Recent/Analysis consumers of hourly history can consequently omit all pre-upgrade history indefinitely, while raw rows remain intact. This is a recovery defect beyond the already documented missing-column historical backfill limitation.

Reproduction: open a temporary new database, insert one raw row, drop only its hourly table to model an existing pre-rollup database, and monkeypatch `SolarDatabase.backfill_hourly_rollup` to raise once. The next normal `open_database()` returns successfully with `sigenstor=1`, `sigenstor_hourly=0`. Manual backfill repairs it; two repeated manual backfills leave exactly one aggregate with `sample_count=1`. See [executable evidence](system-review-architecture-evidence.py), A1. The failure was injected immediately before historical insertion, reproducing the persistent state after an interruption in the creation/backfill window; it was not a real process kill.

Recommendation: persist a completed migration/backfill marker only after successful transactional completion, or make creation plus backfill atomic with the SQLite driver's actual DDL transaction behavior verified. Do not infer completion from table existence. Acceptance: inject failures immediately after creation and during insertion, reopen twice, and recover all historical hour/band groups exactly once with unchanged raw data, sums and counts. Also exercise interrupted restart while ongoing collection adds new groups. Scope/risk: opener and migration tests; avoid reaggregating the lifetime database on every ordinary read.

### A2 — High: transient baseline-load failure poisons the live collector's daily state

Category reliability/correctness; high confidence. `dashboard/live.py:229–240` and `255–283` assign the current day **before** loading its SQLite baseline and completing initialization. `_collect_once()` catches the resulting exception and retries, but the next attempt sees the day already initialized.

PV reproduction on a fresh collector with `pv1`: make `load_pv_array_energy_day_totals` raise once. The next same-day call, with the loader now healthy, never calls it and raises `KeyError(1)` because `_pv_energy_live` remains empty. Every same-day live poll repeats the failure; the server retains old/empty live values until a new day or restart. At midnight with prior state, old baselines/integration state can instead carry into the new day. Grid reproduction: make `load_grid_energy_day_start` raise once, then provide healthy baselines import=90/export=45 and current meters 100/50. The healthy loader is called zero times; output import/export is **0/0 kWh**, expected **10/5 kWh**. See executable evidence A2. Exceptions stand in for a temporary DB failure; the actual lock timing was not tested.

Recommendation: load and initialize each day into local variables, then publish its complete state and day together after success. Also consider making all integration-state mutation atomic with the successful reading: a later failure must not partially advance the previous power/time. Acceptance: one first-sample or midnight baseline failure followed by success retries the baseline, publishes the next fresh reading, produces 10/5 kWh for the grid fixture (tolerance 0.0001 kWh), and does not reuse previous-day PV state or double-count a retry. Scope: live collector and focused deterministic recovery checks; retain its separate non-persisting/live contract.

### A3 — Medium: partial child startup leaks the already-started collector

Category reliability; high confidence for cleanup omission, actual leaked OS process not launched. `docker_start.py:21–36`, `50`, `64–76`: the two `Popen` calls construct a list without cleanup if the second fails. Initial startup happens before the outer `try/finally`. During restart, assignment does not complete, so cleanup still references the old children. Mocking the first child as running and the second `Popen` as raising `OSError` showed neither `terminate()` nor `wait()` called for the first child. See executable evidence A3.

Impact: under child launch failures, a collector can remain running outside its failed supervisor; a later manual launch could add a second collector. This is a rare failure path, not demonstrated normal-operation duplication. Recommendation: track children as each starts and clean that partial list on any launch failure. Acceptance: fail each launch position during initial startup and restart; all children started by that attempt are reaped, no live descendant remains, the original failure is surfaced, and no production device is used in the test. Scope/risk: supervisor lifecycle and isolated mock/subprocess tests.

### A4 — Medium: operational correction repeatedly scans lifetime history and builds historical training before applying its 56-day cutoff

Category performance; high confidence for source and synthetic timings, production magnitude unverified. `forecast/operational_model.py:_load_inputs` lines 56–76 loads **all columns of every forecast** and every non-null PV sample. `_training_frames` lines 124–135 loops over every historical day, each time filtering the full forecast frame; `_fit_scalars` only then discards training outside 56 days. `refresh_adjusted_forecast` calls the calculation for each target day, sequentially in the persisted collector's cycle. This repeats work on retained raw history that is intentionally never deleted.

## Ranked consolidation opportunities

1. **Tariff rule predicates and parsing (low implementation risk).** `config.py:tariff_time_minutes/tariff_rule_matches` and matching helpers in `solar_model/tariffs.py` implement the same weekday/start/end/overnight contract. Config calls it for validation; economics/planner call it at runtime. Share a dependency-neutral predicate/parser module, leaving validation and lookup policies separate. Benefit: prevent a rule accepted by validation from matching differently in collection. Validate every minute of all seven weekdays, crossing midnight, equal bounds, `24:00`, invalid formats and effective-date transitions. No intentional semantic difference was found in current predicates.
2. **Explicit aggregation/forecast contracts before retiring compatibility code (medium/high migration risk).** `solar_model/storage/queries/dashboard.py` contains older frame/ORM aggregation alongside `chart_data_sql.py` and `export_data_sql.py`. Establish active entry points and parity tests then isolate legacy adapters. **Do not unify** chart forecast-energy differencing with export stored-cumulative averages, start-of-day/latest vintages, minute versus rollup means, or raw counter gaps merely because their names overlap. Each semantic difference needs a named contract before sharing mechanics. Benefit: reduce redundant fixes in time/unit/null handling without changing meanings.
3. **Latest device history query (bounded easy improvement).** `database.py:save_device_info` and `dashboard/data.py:load_device_information` load the entire device change history descending and keep the first row per human variable in Python. A shared latest-per-variable SQL query (max ID under the current ordering contract) would bound materialization to variable count for both callers. Preserve change history and grouping by human variable, not silently change to `variable_name`; check duplicate labels, changing units, unchanged observations and historic/as-of callers. No timing-based severity assigned because actual device-history size is unknown.
4. **Retain two Excel writers with explicit ownership.** Dashboard xlsxturbo writes flat downloads; XlsxWriter supports script workbooks in `solar_model/tools/plan_as_of.py`, the subsequently removed boosted intraday backtest, and tariff scripts. Existing benchmark rationale supports the dashboard writer. A library count reduction has no demonstrated benefit; migrate only if feature/formatting parity and measured speed justify it. Readers/test XML inspection are separate needs. Do not add a generic workbook abstraction solely for visual uniformity.
5. **Recovery-state publishing convention.** A1/A2 reflect publishing readiness before successful initialization. Use explicit completion/atomic publication in each subsystem, while retaining different persistence lifetimes (DB migrations versus in-memory live day state). Sharing one class across these unrelated lifecycles would add complexity; share the review/test convention instead.
